# Общий архив компонентов SonarQube

Все репозитории, вызывающие `dotnet-sonar.yml@main`, используют один набор
компонентов из GitHub Releases репозитория `PANiXiDA-Infrastructure/ci-cd`.
Архив не привязан к проекту, ветке или PR. Отдельных изменений в API и
Core-библиотеках не требуется. Потребителям, закрепившим reusable workflow на
старом SHA или теге, нужно обновить эту ссылку.

## Как это работает

1. Composite action читает `.github/actions/sonar-cache/versions.json`.
2. Сначала восстанавливается обычный `actions/cache` текущего репозитория.
3. При отсутствии точного совпадения скачивается общий архив с GitHub Releases.
   Проверяются SHA-256 архива, его конфигурация и контрольные суммы всех файлов.
4. Движок и плагины помещаются в стандартный `~/.sonar/cache`. Для Roslyn
   используется `~/.sonar/resources`; абсолютные пути индекса пересоздаются
   для текущего раннера. Закреплённый `dotnet-sonarscanner` устанавливается
   из включённого в архив NuGet-пакета.
5. Сканер выполняет обычный анализ и ожидает Quality Gate. Настройки проектов,
   правила, результаты, токены и исходный код в общий архив не входят.

Архив содержит движок, все встроенные плагины указанного Community Build,
Roslyn-анализаторы C#/VB, пакет .NET-сканера и исходные лицензионные уведомления.
Java 21 по-прежнему устанавливается через `setup-java`; JRE provisioning выключен.
Сборка рассчитана на текущие `ubuntu-latest` x64 раннеры.

Каждый новый раннер скачивает файлы с GitHub, а не повторно с нашего SonarQube.
Обычный Actions-кэш остаётся дополнительной оптимизацией. Его удаление после
простоя не удаляет релизный архив.

## Публикация и первый запуск

После успешного `Validate` для push в `main` автоматически запускается
`Publish shared Sonar cache`. Он использует **тот же проверенный commit**.
Задача извлекает компоненты из официального Docker-образа по digest и скачивает
фиксированный NuGet-пакет с nuget.org. Доступ к production SonarQube и его
секреты для публикации не нужны.

Релиз содержит `sonar-cache.tar.gz`, `sonar-cache.tar.gz.sha256` и `manifest.json`.
Тег включает версии SonarQube и сканера, а также хэш всей конфигурации, включая
digest образа и `revision`. Файлы существующего релиза не перезаписываются.
Релиз публикуется только после загрузки всех вложений; он не становится Latest.

При первом merge нужно дождаться зелёных `Validate` и `Publish shared Sonar cache`,
затем запустить CI в любом потребителе. Нужны только обычные права `contents: read`;
новые токены и секреты в потребителях не требуются. Записывать релиз может только
задача публикации в `ci-cd`, с `contents: write`; PR релизы не публикуют.

До первой публикации, при недоступности GitHub Release или несовпадении версии
работающего сервера используется обычная загрузка компонентов с SonarQube
с предупреждением в логе. Анализ и Quality Gate не пропускаются. Повреждённый
архив или несовпадение его manifest/checksum останавливают задачу.

## Когда и как обновлять

Единственное место выбора версий — `.github/actions/sonar-cache/versions.json`.

| Изменение | Что менять |
| --- | --- |
| Обновление SonarQube | `server_version` и `server_image`: точный тег Community Build и digest `linux/amd64` |
| Обновление SonarScanner for .NET | `scanner_version`: точная версия NuGet, без `latest` |
| Новый образ с другими встроенными плагинами при прежней версии сервера | `server_image`, включая новый digest |
| Изменение состава/формата архива, исправление упаковки или принудительная пересборка | Увеличить `revision` |
| Новый репозиторий, ветка, PR или изменения прикладного кода | Ничего |
| Изменение Quality Profile, Quality Gate или токена анализа | Ничего |

Порядок обновления:

1. Открыть PR с нужными изменениями `versions.json`. Для изменения упаковки также
   увеличить `revision`, даже если версии сервера и сканера прежние.
2. Дождаться `Validate`: тест собирает настоящий архив из указанного образа,
   восстанавливает его в чистом окружении и анализирует C# и JSON через прокси,
   который запрещает скачивание движка, плагинов и Roslyn-ресурсов.
3. После merge дождаться автоматической публикации нового релиза.
4. При обновлении сервера согласовать этот PR с обновлением образа в
   `core-platform`. Новый архив можно опубликовать заранее; до совпадения версии
   сервера потребители используют обычную загрузку. Обновление сканера начинает
   действовать для новых запусков сразу после merge.
5. Проверить один CI в API и один в Core: восстановление общего архива,
   отсутствие крупных загрузок с SonarQube, успешный Quality Gate.

Движок и плагины имеют каталоги по контрольным суммам. Если на сервере отдельно
изменился плагин, сканер запросит новую версию; старый файл не подменяет её.
Встроенные плагины обновляются вместе с образом. Дополнительные плагины,
установленные отдельно от образа, в этот архив не входят и скачиваются обычным
способом. Для их включения потребуется явно расширить сборщик архива.

Ручной повтор публикации уже выбранной версии:

```bash
gh workflow run sonar-cache-publish.yml --repo PANiXiDA-Infrastructure/ci-cd --ref main
```

Выполнять после зелёного `Validate` для соответствующего commit. При существующем
опубликованном релизе задача ничего не пересобирает. Если предыдущая публикация
оборвалась и оставила draft, удалить именно этот незавершённый draft в GitHub
Releases и повторить запуск. Для замены уже опубликованного архива увеличить
`revision` через PR.

Для отката вернуть предыдущую конфигурацию через PR. Её релиз остаётся доступен;
удалять архивы, на которые ещё могут ссылаться workflow, не следует.

## Локальная проверка

Проверки упаковки, переноса между каталогами, fallback и повреждённых архивов:

```bash
python3 -m unittest discover -s tests -v
```

Сборка настоящего архива требует Linux, Docker и Python 3.12+:

```bash
bash .github/actions/sonar-cache/build.sh /tmp/sonar-archive
python3 .github/actions/sonar-cache/cache.py restore \
  --source /tmp/sonar-archive --destination /tmp/sonar-restored \
  --server-version 26.9.0.129388
```

Полная проверка выполняется в `Validate / sonar-cache`. Скрипт
`tests/sonar_cache_smoke.py` предназначен только для отдельного одноразового
SonarQube: он меняет начальный пароль `admin` и создаёт тестовый проект.
